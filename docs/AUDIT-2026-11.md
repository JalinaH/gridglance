# GridGlance Project Audit — November 2026

**Scope:** whole codebase (Dart, Android, iOS, CI, dependencies), reviewed against `dev` at `76d4305`.
**Baseline:** `flutter test` passes all 223 tests, and `flutter analyze lib test` reports no issues.

Findings are grouped by severity. Each one names the code it points to and what goes wrong for a user.

---

## High

### H1. App launch can hang on a slow or offline network

[`lib/main.dart:27-36`](../lib/main.dart) awaits every init step before `runApp`:

- `AppUpdateMessagingService.init()` waits for the iOS notification permission prompt and for `subscribeToTopic`, which is a network call ([`app_update_messaging_service.dart:22-23`](../lib/services/app_update_messaging_service.dart)).
- On first launch, when the cache is empty, `F1ImageService.init()` waits for an OpenF1 request with no timeout ([`f1_image_service.dart:32`](../lib/services/f1_image_service.dart)).
- If any init step throws, `runApp` never runs and the user sees a blank screen. `Firebase.initializeApp` also runs outside the Sentry zone, so a failure there is never reported.

**Effect:** a first launch on a bad connection stays on the native splash until the OS network timeout.

**Fix:** call `runApp` first. Move the FCM permission request and topic subscription to after the first frame, don't await the image prefetch, and run each init step with its own error handling and timeout.

### H2. Burst of alerts about old sessions after the first check fails

[`favorite_result_alert_service.dart:111-119`](../lib/services/favorite_result_alert_service.dart) sets `sessionSeeded = true` even when all three session fetches returned `null`, for example when the first check ran offline. On the next successful check there's no saved previous value, so the last race, sprint and qualifying each count as "new".

**Effect:** up to 6 "session finished" notifications (3 sessions × driver and team) about sessions that already happened.

**Fix:** only mark the baseline as seeded for a session type once that session's result has actually been fetched.

### H3. Repeated or dismissed alerts come back

The Workmanager task and the foreground app run in separate isolates, and each keeps its own in-memory `SharedPreferences` cache. Nothing in `lib/` calls `prefs.reload()`. When the background task sends an alert and saves `favorite_alert_last_session|…`, the foreground app still holds the old value and sends the alert again on resume. The notification ID is a stable hash of the event, so a notification the user already dismissed comes back.

**Fix:** call `await prefs.reload()` at the start of `FavoriteResultAlertService._runCheck`, or move the alert state to `SharedPreferencesAsync`.

### H4. iOS push notifications and update prompts are broken

- [`ios/Runner/Runner.entitlements`](../ios/Runner/Runner.entitlements) has no `aps-environment` entry, so Firebase push can never reach iOS. The resulting error is caught and ignored.
- [`app_update_service.dart:56`](../lib/services/app_update_service.dart) always reads the `android` block of `update.json`, and its fallback store link is the Play Store (line 26). [`main.dart:169`](../lib/main.dart) runs the update check on every platform, so iOS users get an update dialog that opens the Play Store.

**Fix:** add the Push Notifications capability (and an APNs key in Firebase). Choose the update config by platform and add an App Store link, or skip the update check on iOS.

### H5. Background task failures are invisible

[`background_task_service.dart:34`](../lib/services/background_task_service.dart) calls `CrashReporting.captureException`, but Sentry is only initialized inside the main app's zone. In the Workmanager isolate the call is silently dropped, even though the comment beside it says this is how failures get reported.

Also, since PR #54 a failed widget refresh throws `WidgetRefreshException` before `FavoriteResultAlertService.checkForUpdates()` runs (line 23), so one widget failure also skips the favorite alerts.

**Fix:** initialize Sentry (without `appRunner`) at the start of `backgroundTaskDispatcher`. Run the widget refresh and the alert check independently, then report a combined result.

## Medium

### M1. The selected season never moves forward

The season picked on the home screen is saved and reused forever ([`home_screen.dart:59-62`](../lib/screens/home_screen.dart)). The alert service uses the same value ([`favorite_result_alert_service.dart:70`](../lib/services/favorite_result_alert_service.dart)).

**Effect:** in 2027 the app still opens on 2026, and favorite alerts keep checking 2026 forever.

**Fix:** treat the saved season as a browsing choice. Reset it to the current season on a new year or app start, and always use the current season for alerts.

### M2. Some network calls lack a timeout, retries or cache fallback

`_getJsonWithCache` handles timeouts, retries and cache fallback well, but these calls use bare `http.get`:

- `_fetchRaceResultsByEndpoint`, `getRaceTop3DriverIds` and `getQualifyingTop3DriverIds` ([`api_service.dart:251, 268, 302`](../lib/data/api_service.dart))
- Weather ([`weather_service.dart:77`](../lib/services/weather_service.dart))
- OpenF1 headshots ([`f1_image_service.dart:65`](../lib/services/f1_image_service.dart))
- Widget image downloads in `widget_update_service.dart`

This matters most in background tasks: iOS gives about 30 seconds, and a stuck request uses all of it.

**Fix:** use one shared HTTP helper with a timeout everywhere, at least adding `.timeout(...)`.

### M3. Car images point at the 2025 season

[`f1_image_service.dart:57`](../lib/services/f1_image_service.dart) hardcodes `/teams/2025/` in the car image URL, so 2026 cars are wrong or missing.

**Fix:** build the path from the current season, falling back to the previous year.

### M4. `main` is missing the background widget refresh fix

On `main`, the `gridglance/dps` storage channel is registered only in `MainActivity`. The Workmanager isolate can't reach it, so every background widget refresh fails. PR #54 fixed this on `dev`, but it hasn't been merged to `main`, so a release built from `main` still has the bug.

**Fix:** merge `dev` to `main` before the next release.

## Low / cleanup

- **Analyzer noise:** a plain `flutter analyze` reports 71 errors, all from `build/ios/SourcePackages/firebase_messaging-*/test`. Add `analyzer: exclude: [build/**]` to `analysis_options.yaml`. CI isn't affected because it uses a clean checkout.
- **Time zone setup:** `tz.setLocalLocation(tz.local)` in [`notification_service.dart:244`](../lib/services/notification_service.dart) does nothing, so the zone stays UTC. One-off reminders still fire at the right moment, but recurring or wall-clock schedules would be wrong if added later. Use `flutter_timezone` to set the device zone.
- **Outdated dependencies** (major versions behind): `flutter_local_notifications` 17 → 22, `sentry_flutter` 8 → 10, `posthog_flutter` 4 → 5, `home_widget` 0.6 → 0.10, `workmanager` 0.9 → 0.10, `share_plus` 10 → 13, `package_info_plus` 8 → 10, `timezone` 0.9 → 0.11.
- **Leftover template text:** the `pubspec.yaml` description is still "A new Flutter project."
- **Kotlin folder mismatch:** six Kotlin files are in `android/app/src/main/kotlin/com/example/gridglance/` but declare `package com.gridglance.app`. It builds; move them to `com/gridglance/app/` for consistency.
- **Firebase API keys** are committed (`google-services.json`, `GoogleService-Info.plist`, `firebase_options.dart`). That's normal for Firebase client config, but check in the Google Cloud console that the keys are restricted to the app's Android package and iOS bundle ID.

## What's in good shape

- JSON parsing is defensive throughout (`JsonSafe`), with a sensible threshold for decoding large bodies in an isolate.
- The main API path has good request deduplication, retries with jitter, cache fallback and error classification for Sentry.
- Every `AnimationController`, `Timer`, `TextEditingController` and `ScrollController` in screens and widgets is disposed.
- Notification IDs are stable (FNV hash), so rescheduling replaces existing notifications instead of duplicating them.
- Analytics opt-out is checked on every call, and Sentry/PostHog do nothing without `secrets.json`.
- 223 tests covering models, utils, services, screens and widgets, with CI for analyze, format, test and Android build.

## Suggested order

1. H1, H2, H3, M1: user-facing bugs, each small and fixable independently.
2. H4, H5: platform configuration and background reporting.
3. M4: merge `dev` to `main` before the next release.
4. M2, M3, then the cleanup items.
